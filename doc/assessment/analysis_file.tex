\section{Introduction}\label{introduction}

\section{Part 1 -- Functional
Analysis}\label{part-1-functional-analysis}

\subsection{Rephrasing the
requirements}\label{rephrasing-the-requirements}

Three features are a must for our application, they relate to the user
experience and the different functionalities needed for an administrator
to operate and manage cinema reservations. Those three features are as
followed:

\begin{itemize}
\tightlist
\item
  As a customer, I can book a screening for an upcoming movie
\item
  As an administrator, I can prepare the schedule of movie screenings
\item
  As an administrator, I can see accounting details for a given period
\end{itemize}

First of all, this project must have two different sides: a customer
side that will be the public and an administrator side. Accounts with
the correct rights for the administrators are therefore required.

\subsection{Analysis of the features}\label{analysis-of-the-features}

For each features, here is the analysis of the requirements that need to
be met in order to succesfully implement the feature.

\subsubsection{Book a screening for an upcoming
movie:}\label{book-a-screening-for-an-upcoming-movie}

We will need to implement a time management tool in order to classify
movies as upcoming or ended. Many clients may want to book a ticket to
the same screening at the same time, it is then essential for us to
create a special status and management for unconfirmed bookings in order
to prevent the oversale of tickets. Booking implies the implementation
of a payment and confirmation system.

\subsubsection{Prepare the schedule of movie
screenings:}\label{prepare-the-schedule-of-movie-screenings}

Given information about the movies that wished to be scheduled we will
implement, without a front-end, a way to add movies to each room without
there being overlaps between sessions. Information about movies will be
taken via an API that will be from TMDB. With this information we will
be able to recover the duration of the film and establish the time at
which the screening will end.

\subsubsection{Accounting details:}\label{accounting-details}

Accounting details will be provided to administrators using the
screening history and supplementary revenues from the other activities
of the cinema. Graphs will be provided in order to have them be
implemented later in the front-end by the other team.

Those three features mean, in technical terms, creating a backend that
will be able to support a comprehensive frontend for customers to reach
our cinema (that will be developed as a separate project). This can be
translated by the existence of our personal API that will communicate
information to the frontend of the application. It also means having a
separate system dedicated for the administrators where the schedule can
be made and information stored. Lastly, those features imply access to
an external API in order to properly set schedules and have automatic
and unique information about movies to present to the customers. In
order to use the limited requests of the TMDB API efficiently, we will
establish a private database via POSTGRE SQL to store data about movies
that will be screened. It will also be useful to track user actions
(seen movies, posted comments\ldots) in order to provide a more personal
experience.

\subsection{Implementation of the
features}\label{implementation-of-the-features}

\subsubsection{Priority features}\label{priority-features}

Here are the features that are at the core of the application's design:

\paragraph{User features:}\label{user-features}

For the customer, we will implement different features which will mainly
be having access to the scheduled movies, seeing information about said
movies, and being able to book a screening. An important part of this
will be the query system that will allow the customer to search
screenings by name of movie, genre, length, date and time of screening
(maybe more).

The user will also be able to create an account to enjoy rating and
writing comments about seen movies, have a friend list and be able to
interact with them. It will be possible to establish one with an email
address, pseudonym and password. Implementing this will mean having to
implement a database corresponding to the movies seen by the user and a
secure way to add them to the seen list to avoid review bombing on the
future website. Finally, a payment system will be implemented in order
to have a fully functional back-end that will fit all the needs of our
customer.

\paragraph{Admin specific features:}\label{admin-specific-features}

Administrator accounts will be the same as user accounts, allowing them
to also interact socially, but will have access to more features. Those
features are mainly: establishing a schedule for the different rooms,
being able to modify the pricing and also have the ability to check
accounting details in order to run the cinema efficiently. Accounting
details will not provide official documents but statistics about what
the administrator would want to know. A search per time interval, movie
and genre will be implemented. A summary of the statistics we wish to
implement:

\begin{itemize}
\tightlist
\item
  number of tickets sold
\item
  turnover
\item
  theatre occupancy rate
\item
  sales per film
\item
  sales per screening
\item
  sales per day/week/month
\item
  average ticket price
\end{itemize}

\subsubsection{API uses}\label{api-uses}

\paragraph{Movie informations:}\label{movie-informations}

The list of scheduled movies being quite small and the potential
userflow of the website quite high, we will import the movie data once
on a personal database that will then be accessible without external
constraints. TMDB's API provides the summary in french and the french
name of the movie. Using an external API will allow us to provide the
customer with all the information about any movie that the cinema will
provide, for example its duration, actors, rating, trailer, box office,
ratings and more.

\paragraph{Payment system:}\label{payment-system}

We will implement a working payment system using Stripe. This method
will allow us to implement a way to confirm bookings without having to
worry about the privacy of the credit cards.

\subsubsection{Features included if time
allows:}\label{features-included-if-time-allows}

For the moment we do not plan to implement a system to let the customer
choose their seats. This method is quite common and already in place at
Bruz's cinema. However, if time allows, it would be a plus that would
help us provide a better experience for motivated customers.

\subsubsection{Features excluded:}\label{features-excluded}

In this project, we will not allow the customers to cancel their
bookings nor get a refund. We will also not send confirmation emails but
rather provide the customer with a confirmation screen and access to its
bookings. We will not adapt our application for the specific use of
adding more cinemas but rather focus solely on Bruz's cinema.

\subsection*{Final Decision}\label{final-decision}

TMDB is selected: It is the only candidate among the two to return key
fields such as title, synopsis, and genres translated into French (via
the language=fr-FR parameter), whereas OMDb strictly provides these
fields in English.

\subsection{Accounting Module}\label{accounting-module}

The Accounting Module collects sales data and tracks financial
performance. This report presents the main accounting and analytics
features chosen for the system.

\subsection*{Key Indicators}\label{key-indicators}

\begin{itemize}
\tightlist
\item
  \textbf{Number of Tickets Sold:} Shows the total volume of sales. This
  number measures attendance and is used for official ticketing reports.
\item
  \textbf{Total Revenue:} The total money collected over a chosen
  period. It helps monitor the general financial health of the cinema.
\item
  \textbf{Hall Occupancy Rate:} The percentage of filled seats compared
  to the total capacity of the room. It shows how well each room and
  movie schedule performs.
\item
  \textbf{Revenue by Movie:} Shows how much money each movie makes. This
  is useful to check movie profitability and calculate payments for
  distributors.
\item
  \textbf{Revenue by Show:} Shows the earnings for each specific
  showtime (afternoon, evening, early screenings) to help improve the
  schedule.
\end{itemize}

\subsection*{Time Tracking}\label{time-tracking}

For both Total Revenue and Number of Tickets Sold, you can filter data
by selecting a start date and an end date. You can also view results by
day, week, or month with a graph to identify seasonal trends and follow
performance over time.

\subsection{Task assignment}\label{task-assignment}

We split the work mostly along these roles. Nolann handles coordination,
planning and keeping the Gantt diagram up to date. Simon takes care of
the technical side, meaning the architecture, the class diagram and the
general design choices. Samuel is more on the data side, so the database
and the data model, and how we access the data. And Zoeb is in charge of
testing, basically making sure stuff actually works before we call it
done.

Of course this is not a strict separation: everyone can work on any part
if needed, especially since we're only 4 people. But these roles give
each of us a main area to focus on and to be responsible for.

\subsection{Methodology}\label{methodology}

We have a team meeting every week to check where everyone is, discuss
blocking points and decide what to do next. For now we mostly talk on
WhatsApp when we need to decide something quickly, and we put our
documents on Google Drive so everyone can access them. We know that
WhatsApp is not the best communication tool for this sort of project
work , so we're currently looking for a possibly more efficient tool,
but we haven't switched yet.

The code is on GitHub (github.com/nolannb35/ENSAI-2A-projet-info-team6),
we use it to keep track of the different parts of the project and work
at the same time without breaking each other's code.

We also want to do some kind of review before the big deadlines
(Analysis File, immersion, final delivery), just to check everyone's
part actually fits together before it's too late to fix.
